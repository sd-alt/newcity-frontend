# Agent 执行异常与方案版本操作说明

## 执行异常

当执行项失败或进入人工介入状态时，Agent 工作区会展示执行项名称、状态、进度、重试次数和错误原因。操作按钮直接绑定具体执行项：

- 重试：清空错误、进度归零并增加重试次数。
- 转人工：保留人工说明，运行显示“任务已转人工处理，自动监控已暂停”；人工完成后点击“人工已完成”再恢复监控。
- 取消执行项：标记该执行项已取消并记录原因。

网页提交的是结构化 `executionItemId + action + note`，不是一段无法校验的自由文本。

执行异常和方案资源选择都通过 MAF Checkpoint 恢复消费。提交按钮只保存人工响应并重新入队，业务状态在 Worker 恢复 Checkpoint 时执行；重复刷新不会重复重试、替换或取消。

执行异常显示结构化按钮时不会同时显示“补充需求信息”输入框。取消后页面明确提示“必需执行项已取消，任务无法自动完成”。

## 外部执行轮询

任务处于排队等待外部执行时，页面会显示下一次查询时间、轮询次数和当前间隔。此状态表示等待外部系统，不表示 Agent 失败。

## 方案版本

方案管理表展示当前版本。展开“历史”可以查看版本号、变更类型、原因、来源运行、创建时间和资源数量，并选择历史版本回滚。回滚会新建草稿版本，必须重新评价和审核后才能发布，原历史版本不会被覆盖。资源替换表单不会预选旧资源或候选资源，用户必须明确选择两者并填写原因。

## 模型审计

技术详情默认折叠。开启后可查看模型阶段、模型名、Prompt 版本、Schema 版本、校验状态、Token、延迟和是否发生回退；页面不展示密钥和原始 Prompt。

## 并发提交与状态冲突

“人工已完成”提交后按钮立即禁用并显示“正在提交”。同一页面的连续点击不会再次调用接口，后端也会用稳定请求键保证网络重放只消费一次。

人工请求刚出现但 Checkpoint 尚未绑定时，页面显示“正在保存工作流检查点”，并禁用审批、需求补充、执行处置和方案替换按钮。页面会继续通过实时事件和轮询刷新；审批的 `checkpointId` 与当前 Workflow 的 `checkpointId` 一致后自动解锁，无需用户手动刷新。

若其他页面或 Worker 已经推进了运行，当前操作会收到 Checkpoint 或状态冲突。页面统一提示“任务状态已更新，请刷新后重新操作”，不会把过期响应继续提交到新的人工节点。

Checkpoint绑定失败不会伪装成普通人工执行项。页面会明确显示检查点故障，并提供“重新绑定 Checkpoint”和“从最后有效 Checkpoint 重试”；两项都不会替用户自动确认业务审批。若检查点文件或请求本身已经不可恢复，仍可选择人工接管或取消任务。

需求补充后若仍有缺失字段，页面会展示新一轮人工请求并继续停留在完整性检查阶段。重试、方案资源选择和人工完成会在原 MAF Checkpoint 内继续，不会新建第二条执行链；转人工、取消和拒绝会停止自动继续。运行完成后工作区兼容顶层摘要和 `result.summary` 嵌套摘要，并展示最终节点状态与传感器数量。

`requirement_clarification` 只展示“补充需求信息”输入框和“提交并重新分析”按钮，不再同时展示通用的确认或拒绝按钮，避免把“人工核验通过”等备注误当成需求内容。

## 真实联调版本

自动触发“前端检查”工作流时默认读取 `.github/backend-agent.sha` 中已验证的后端完整提交 SHA。手动触发时可以填写 `backend_ref` 临时覆盖为其他分支、标签或提交 SHA；工作流摘要会同时记录实际前端和后端版本。
